# Security review

Дата: 2025-02-14  
Область: authentication, CORS, sessions, `FileReader`, `SqlQuery`.  
Метод: статический read-only review; PHP-код и тесты не изменялись.

## Подтвержденные findings

### SEC-01 — слишком широкий CORS для привилегированного API

**Severity: High**  
**Файлы:** `public/mcp-endpoint.php:53-56`, `lib/Transport/HttpTransport.php:61-63`

Оба HTTP-варианта отвечают с `Access-Control-Allow-Origin: *`, при этом endpoint принимает `Authorization` и возвращает данные `FileReader`/`SqlQuery`. Любой origin может выполнить preflight для этих заголовков. Это не позволяет получить доступ без Bearer-токена, но если токен присутствует в браузерном клиенте, вредоносный origin получает возможность отправлять запросы и читать ответы API. Для endpoint с доступом к исходникам и БД wildcard не соответствует принципу минимального доверия.

**Рекомендация:** разрешать только явно заданный список доверенных HTTPS-origin (с `Vary: Origin`), не использовать `*`; отдельно решить, нужен ли браузерный доступ вообще. Не помещать Bearer-токен в обычный веб-клиент и применять TLS.

### SEC-02 — `SqlQuery` допускает побочные эффекты и дорогостоящие операции

**Severity: High**  
**Файл:** `lib/Tools/SqlQuery.php:70-98,169-210`

Контроль является blacklist-проверкой текста и проверяет лишь начало `SELECT` и несколько ключевых слов. Поэтому проходят, например, `SELECT ... FOR UPDATE`/`LOCK IN SHARE MODE` (блокировки), `SELECT GET_LOCK(...)` (именованный серверный lock), а также дорогостоящие функции вроде `SLEEP(...)` и `BENCHMARK(...)`. Ограничение строк не ограничивает стоимость вычисления до выдачи результата; параллельные запросы могут занять соединения/CPU. Таким образом, описание «безопасный SELECT» фактически не гарантирует read-only и доступность БД.

**Рекомендация:** выполнять запросы отдельной БД-учёткой с минимальными правами и read-only режимом; вместо blacklist использовать SQL parser/строгий allowlist допустимого AST (запрет locking clauses, user variables, side-effect functions и подзапросов/конструкций вне политики). Применить server-side resource controls: statement timeout, лимит размера результата, rate/concurrency limits и отдельный пул соединений. Проверить, что таймаут реально прерывает запрос, а не только цикл чтения результата.

### SEC-03 — неограниченное чтение файла позволяет вызвать memory/response DoS

**Severity: Medium**  
**Файл:** `lib/Tools/FileReader.php:75-121`

Файл полностью читается в память (`file_get_contents`), затем дополнительно разбивается на строки (`explode`) и может копироваться через `array_slice`/`implode`. Нет ограничения размера файла или размера возвращаемого содержимого. Авторизованный вызов для большого файла в разрешённых каталогах может исчерпать память PHP и размер ответа; `start_line`/`end_line` не устраняют проблему, поскольку чтение целого файла происходит раньше.

**Рекомендация:** проверять размер до открытия, ввести жёсткий лимит байтов ответа и читать потоково только нужный диапазон строк. Добавить server-side request/response limits и тесты на большой файл.

### SEC-04 — проверка пути и чтение разделены (TOCTOU для symlink)

**Severity: Medium (при наличии локального злоумышленника, который может менять файлы)**  
**Файл:** `lib/Tools/FileReader.php:71-90`

`realpath()` и проверки allowlist выполняются до `file_get_contents()`. Между ними другой процесс с правом записи может заменить файл или symlink, после чего будет прочитан уже другой объект. Это не обычный удалённый path-traversal, но является подтверждённым race condition в модели, где `DOCUMENT_ROOT` или разрешённые каталоги writable другим пользователем/процессом.

**Рекомендация:** по возможности сделать каталоги недоступными для записи веб-пользователю/сервису; использовать безопасное открытие с проверкой дескриптора (без следования symlink, где это поддерживается ОС/рантаймом) и проверять фактический объект после открытия. Не полагаться на строковую проверку пути как на единственную границу.

### SEC-05 — MCP session ID не является сессией и не инвалидируется

**Severity: Medium (нарушение security-семантики и lifecycle)**  
**Файлы:** `public/mcp-endpoint.php:181-186,239-254`, `lib/Controller/ApiController.php:24-26,185-200`

При `initialize` генерируется ID, но он не сохраняется и не связывается с Bearer-токеном. Любой присланный `Mcp-Session-Id` принимается и просто возвращается; `DELETE` отвечает `session terminated`, но ничего не удаляет. В `ApiController` массив `$sessions` также не используется. Сейчас каждый запрос всё ещё защищён Bearer-токеном, поэтому прямого обхода authentication этим фактом не доказано, однако заявленное завершение/привязка сессии не работает и создаёт риск при добавлении session-based логики.

**Рекомендация:** выбрать явную модель: либо полностью stateless и не выдавать lifecycle-сессию, либо хранить server-side запись с криптографически случайным ID, владельцем/контекстом, expiry и одноразовой инвалидизацией; проверять ID на POST/GET/DELETE и не доверять произвольному входному ID.

### SEC-06 — клиенту возвращаются внутренние тексты исключений

**Severity: Low**  
**Файлы:** `public/mcp-endpoint.php:259-273`, `lib/Controller/ApiController.php:201-216`, `lib/Tools/FileReader.php:77-93`, `lib/Tools/SqlQuery.php:146-148`

В error response попадает `$e->getMessage()`. Для `FileReader` это раскрывает путь, для `SqlQuery` — сообщение драйвера БД; endpoint также принимает произвольный текст исключения из обработки запроса. Это облегчает разведку и может раскрыть детали схемы/конфигурации авторизованному или скомпрометированному клиенту.

**Рекомендация:** наружу отдавать стабильное общее сообщение и correlation ID; подробности писать в защищённый журнал с редактированием секретов. Не включать file/line и DB error в API-ответ.

## False positives / не подтверждено как уязвимость

- **Path traversal в `FileReader`:** проверка `..`, `realpath`, корень `DOCUMENT_ROOT` и повторный allowlist делают показанный обычный traversal недоступным. Symlink race вынесен отдельно как условный TOCTOU, а не как подтверждённый удалённый обход.
- **Bearer comparison:** `hash_equals` используется в `HttpTransport`, standalone endpoint и controller; prefix/тайминг-обход по сравнению токена не найден. Сам токен остаётся bearer-secret: его компрометация даёт полный доступ.
- **OPTIONS без authentication:** preflight не выполняет защищённую операцию и обычно должен быть доступен без токена. Риск возникает из-за последующего wildcard CORS (SEC-01), а не из-за самого bypass OPTIONS.
- **Отключённые Bitrix CSRF/Auth filters:** это не отдельный bypass в просмотренном controller: собственная Bearer-проверка вызывается в `sendMcpResponse()`, а session/cookie authentication не используется как доверенный фактор. Это верно только при сохранении требования Bearer для всех методов.
- **Секреты в разрешённых каталогах:** allowlist намеренно позволяет читать часть `local/` и `bitrix/`; это опасная capability модели инструмента, но без требований проекта к конкретным файлам нельзя утверждать обход. Явно запрещены `dbconn.php` и указанные `.env`, однако другие секреты в allowlist могут быть прочитаны авторизованным клиентом.
- **CORS в `ApiController`:** отсутствие CORS-заголовков у route endpoint может ломать browser integration, но само по себе не является security vulnerability.

## Итог

Аутентификация токеном присутствует и сравнивается безопасно, но CORS чрезмерно широк. Основные подтверждённые риски — привилегированный browser-доступ при наличии токена, недостаточно строгая модель «read-only SQL», неограниченное чтение файлов и фиктивный lifecycle сессий.
